# Prisma ORM 7 migration

Issue: #114

## Scope

This migration moves the repository from Prisma ORM 6.12 to Prisma ORM 7.9 as one compatibility change. The Prisma CLI and generated client stay on the same release, PostgreSQL runtime access moves to the required `@prisma/adapter-pg` driver adapter, and the generated client moves out of `node_modules` into the database workspace.

No database model or migration-history change is part of this upgrade.

## Runtime changes

- `prisma` and `@prisma/client` are both `7.9.1`.
- PostgreSQL connections use `@prisma/adapter-pg` with `pg`.
- The database workspace remains ESM (`"type": "module"`).
- `PrismaClient` is imported from `packages/database/generated/prisma/client` and is generated by the `prisma-client` generator.
- The existing lazy global singleton remains in place so route analysis does not construct a database client and warm serverless processes reuse one client.
- The adapter explicitly keeps the Prisma 6 PostgreSQL connection timeout (`5s`) and idle timeout (`300s`) instead of silently inheriting the different `pg` defaults introduced by the adapter migration.

## CLI configuration

`packages/database/prisma.config.ts` is now the source of the Prisma CLI datasource and migration paths. It loads the repository-root `.env` file when present so the documented local workflow (`cp .env.example .env`) continues to work.

`prisma generate` is allowed to run without a database URL because generation does not connect to PostgreSQL. Commands that need the database still require a valid `DATABASE_URL`; CI and production migration workflows provide it explicitly.

The schema datasource now declares only the PostgreSQL provider. The URL moved out of `schema.prisma` as required by the Prisma 7 configuration model.

## Generated client

The schema uses:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}
```

`packages/database/generated` remains ignored by Git. Every application production build already runs `pnpm --filter @luminol/database generate` before its framework build, and the root production build runs `pnpm db:generate` before the workspace build graph.

## Database safety

- Existing migrations under `packages/database/prisma/migrations` are retained byte-for-byte.
- Do not reset, squash, regenerate, or rewrite production migration history for this upgrade.
- Pull-request validation may deploy the existing history only to the ephemeral CI PostgreSQL service.
- Production migrations remain `prisma migrate deploy` only.
- No production data mutation is required to upgrade Prisma itself.

## Validation gate

Do not merge unless the exact PR head passes:

1. frozen pnpm installation;
2. secret/action-pin checks and the production dependency audit;
3. Prisma Client generation;
4. Prisma schema validation and deployment of the complete existing migration history to ephemeral PostgreSQL;
5. repository lint and formatting;
6. every workspace TypeScript check;
7. unit and integration tests, including database integrations;
8. all production application/workspace builds;
9. public Playwright launch smoke tests.

After merge, require a successful `main` CI run before treating the migration as the production baseline. Production Vercel deployment and runtime health should be verified when deployment quota permits.

## Rollback

This is a code/tooling migration and intentionally changes no database schema or data. If Prisma 7 causes a production regression:

1. revert the Prisma 7 merge commit;
2. restore the Prisma 6.12 package/lockfile state, the `prisma-client-js` generator and `@prisma/client` imports from that revert;
3. run the full repository CI gate again;
4. redeploy the reverted application artifacts;
5. do **not** roll back or edit database migrations solely because the ORM runtime was reverted.

If a later change adds a database migration after Prisma 7 is merged, treat that migration separately under the production migration runbook; never use destructive schema reset as an ORM rollback mechanism.
